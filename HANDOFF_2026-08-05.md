## Funcionalidad implementada

- Login con las credenciales introducidas por cada tecnico contra `initSession` de GLPI.
- Backend for Frontend: el navegador nunca contacta directamente con GLPI.
- Sesiones opacas `HttpOnly` almacenadas en Redis.
- Logout local y `killSession` en GLPI.
- Listado de incidencias asignadas directamente al tecnico autenticado.
- Estados operativos por defecto: nueva, en curso, planificada y en espera.
- Orden de apertura ascendente, de mas antigua a mas reciente.
- Paginacion mediante `Cargar mas`.
- Detalle, descripcion saneada y cronologia de seguimientos.
- Decodificacion de HTML normal y HTML codificado como entidades numericas de GLPI.
- Alta de anotaciones publicas con proteccion ante doble envio.
- Dictado `es-ES` mediante Web Speech API para anotaciones y cierres.
- Deduplicacion de resultados finales repetidos o acumulativos de navegadores moviles.
- Boton `Cerrar` junto a `Anotar` cuando el perfil tiene permisos.
- Cierre con anotacion obligatoria: primero crea seguimiento publico y despues cambia el estado a cerrado.
- Dos pestanas en el listado: `Incidencias` y `Filtros`.
- Filtros por estado, prioridad, fecha de apertura desde/hasta, ID y texto del titulo.
- PWA sin cache de tickets ni manejador `fetch` en el service worker.
- Interfaz mobile-first, accesibilidad y estados de carga/error/vacio.
- Healthchecks `/api/health/live` y `/api/health/ready`.

## Descubrimientos de la API GLPI

La autenticacion de solo lectura se valido correctamente. Mapeo dinamico observado:

| Campo             | Opcion de busqueda |
| ----------------- | ------------------ |
| Titulo            | `1`                |
| ID                | `2`                |
| Prioridad         | `3`                |
| Solicitante       | `4`                |
| Tecnico           | `5`                |
| Estado            | `12`               |
| Fecha de apertura | `15`               |
| Modificacion      | `19`               |
| Ubicacion         | `83`               |

La aplicacion no fija estos IDs: los descubre con `listSearchOptions/Ticket` y conserva una cache corta.

Detalles importantes:

- El ID del usuario autenticado es `glpiID`; `valid_id` es un identificador textual de sesion PHP y no debe usarse como usuario.
- En esta instalacion, dos criterios `notequals` sobre estado producian resultados incorrectos. El trabajo abierto se consulta con un grupo explicito `(estado 1 OR 2 OR 3 OR 4)`.
- La cuenta de prueba mostro 74 tickets asignados directamente: 3 operativos abiertos, 3 resueltos y 68 cerrados en el momento de la prueba.
- Los filtros reales por estado, prioridad, fecha e ID fueron aceptados y devolvieron resultados coherentes.
- No se cerro ni modifico ningun ticket real durante las pruebas automatizadas/manuales de integracion.

## Seguridad y red local

GLPI usa HTTP porque el responsable autorizo expresamente su uso dentro de la red municipal. El HTTPS del servidor GLPI presenta un certificado Let's Encrypt caducado el 18 de diciembre de 2024. No se ha desactivado la validacion TLS ni se ha introducido `rejectUnauthorized: false`.

Orígenes locales autorizados en el despliegue actual:

```text
http://localhost:3000
http://10.158.0.197:3000
http://172.16.10.8:3000
http://AYUINF001:3000
https://10.158.0.197:3443
```

`APP_ORIGIN` admite varios origenes exactos separados por comas. Las escrituras comprueban `Origin`; no eliminar esta proteccion.

El dictado no funciona desde una IP por HTTP porque Web Speech API exige contexto seguro. Para la prueba local se incorporo Caddy con CA interna:

- Certificado publico exportado: `caddy-root-ca.crt`.
- Descarga para el movil: `http://10.158.0.197:3000/caddy-root-ca.crt`.
- El movil debe instalar y confiar en esa CA y acceder por `https://10.158.0.197:3443`.
- El archivo publico no contiene clave privada.
- La clave privada permanece en el volumen Docker `caddy_data` y nunca debe copiarse al VPS.

Con un dominio y certificado publico en el VPS, Caddy y la CA local dejaran de ser necesarios para el acceso externo.

## Configuracion necesaria en el VPS

No copiar `.env.local`. Crear secretos nuevos en el VPS mediante un fichero `.env` con permisos `600`, Docker secrets o el gestor elegido.

Variables minimas:

```dotenv
GLPI_BASE_URL=http://soporte.mairenadelalcor.net/glpi
GLPI_APP_TOKEN=
GLPI_ALLOW_HTTP=true
GLPI_TIMEOUT_MS=10000
GLPI_CLOSE_STRATEGY=status-closed
SESSION_SECRET=<nuevo-secreto-aleatorio-de-al-menos-32-caracteres>
SESSION_IDLE_MINUTES=30
SESSION_ABSOLUTE_HOURS=8
APP_ORIGIN=https://incidencias.dominio-municipal.es
APP_PORT=3000
```

No definir `GLPI_USER` ni `GLPI_PASS` en el contenedor de produccion. Cada tecnico introduce sus propias credenciales. Las variables existentes en `.env.local` solo sirven para el script manual de diagnostico.

## Plan para VPS y Nginx

1. Confirmar dominio publico definitivo, DNS y acceso SSH al VPS.
2. Comprobar conectividad desde el VPS hacia `soporte.mairenadelalcor.net` por HTTP. Si GLPI solo es accesible desde la red municipal, crear VPN site-to-site, WireGuard o ruta segura; no publicar GLPI por este motivo.
3. Instalar Docker Engine, Compose plugin y Nginx, o reutilizar los servicios existentes.
4. Copiar el codigo excluyendo `.env.local`, `.next`, `node_modules`, certificados locales y datos de pruebas.
5. Crear `.env` de produccion con un `SESSION_SECRET` nuevo y `APP_ORIGIN` igual al dominio HTTPS exacto.
6. En produccion no exponer directamente el puerto 3000 a Internet. Publicarlo solo en `127.0.0.1:3000` o en una red Docker compartida con el proxy.
7. Deshabilitar/eliminar el servicio Caddy local del Compose de produccion o crear un override sin `proxy`.
8. Configurar Nginx para terminar TLS y hacer `proxy_pass` a Next.js.
9. Emitir certificado con Let's Encrypt o la PKI corporativa.
10. Preservar `Host`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Forwarded-For` y soporte WebSocket/HTTP 1.1.
11. Limitar el cuerpo de peticiones y establecer timeouts coherentes con GLPI.
12. Abrir en firewall solo SSH administrado, HTTP para ACME/redireccion y HTTPS.
13. Ejecutar healthchecks, login real, listado, filtros, detalle, dictado y logout.
14. Probar el cierre exclusivamente con una incidencia desechable autorizada.
15. Revisar logs para confirmar que no aparecen credenciales, tokens ni contenido de tickets.

Configuracion Nginx orientativa, pendiente de sustituir el dominio:

```nginx
server {
    listen 80;
    server_name incidencias.dominio-municipal.es;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name incidencias.dominio-municipal.es;

    ssl_certificate /etc/letsencrypt/live/incidencias.dominio-municipal.es/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/incidencias.dominio-municipal.es/privkey.pem;

    client_max_body_size 64k;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_read_timeout 60s;
        proxy_send_timeout 60s;
        proxy_buffering off;
    }
}
```

Antes de aplicar esta configuracion hay que adaptarla al Nginx y al esquema de despliegue reales del VPS.
